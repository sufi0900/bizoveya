## Delivered source contract — P04.3.4.4c

Migration046 adds a trusted upload-attempt ledger, reserved byte/item admission, a separate12-admission hour-window counter, guarded commit, creator/member-checked object resolution and cleanup claims. It does not rewrite001–045 or create a browser bucket policy. A server-only client uses `BIZOVEYA_MEDIA_SERVICE_KEY` and the existing Supabase URL; this is a dedicated activation field, not an image-generation provider credential.

Owner admission and membership are checked before sanitization/Storage work. The server accepts canonical base64 JSON carrying at most3 MiB input, bounds the whole request, verifies rights/alternative text/review, decodes/re-encodes PNG/JPEG, strips supplied metadata, corrects orientation, preserves PNG alpha, applies a10-second native processing timeout, checks output limits and hashes actual sanitized bytes. Client filename/MIME/dimensions/hash/path are never accepted as authority. SVG/URLs/animated or malformed/oversized content is rejected.

Processing admission occurs before native image decoding and caps36 processing attempts per hour window, including failed images and retries. Prepare locks the creator before membership/site locks, avoiding SHARE-to-UPDATE lock upgrades. Quotas include saved/archived immutable versions plus pending reservations:32 records/site,20 versions/item,160 MiB retained bytes/site,64 active attempts/creator and12 new admissions per hour window. Same attempt/document retries are idempotent. Each media item has one pending write at a time. The two-minute commit window is not renewed by retries.

Storage uses an exact creator/workspace/site/media/version/hash path and `upsert:false`. An existing path is reused only after downloading and verifying actual bytes/hash. Metadata commits only after write success or verified retry. An uncertain commit response never triggers immediate deletion, because the transaction might already have committed. GET byte retrieval reauthorizes current membership and creator ownership, checks stored size/hash, and returns PNG/JPEG with private/no-store and nosniff headers. No signed public URL or Storage path is returned in application JSON. Creator images are not exposed to other workspace members.

Owner recovery claims at most8 tracked attempts older than10 minutes with no saved path reference, marks them cleaning so late commits fail, removes only those exact objects through Storage API, and deletes completed attempt rows only after removal. Failed removal remains retryable after the two-minute cleanup lease. The separate admission counter is not reset by cleanup. Saved/archived versions are never selected for deletion.

`node tools/media-cleanup.mjs` is a no-request dry run. An authorized operator can separately use `--apply` with private environment credentials to clean up at most8 tracked orphans, including saved-object orphans after authorized account/site cascades. Committed attempt paths remain available to that maintenance ledger until orphan removal; live referenced objects are skipped. No schedule, deployment setting or hosted cleanup was installed/executed by the assistant. Operator maintenance must continue after deletion events; source support is not proof it has run.

The image library is reached through Site → Agent readiness → Private image library. Owner uploads new images or new versions; current creator members can inspect/download their own history; only an owner can review/archive/recover. Review decisions are immutable. New image versions need new reviews. Archive retains bytes/history and quota usage. Alternative text, rights basis/evidence, upload confirmation and review controls are documented below. Input changes reset relevant confirmations; unsaved file/review navigation prompts; conflicts preserve local input.
