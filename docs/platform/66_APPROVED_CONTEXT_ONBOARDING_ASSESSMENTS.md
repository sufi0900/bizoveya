## Data, permissions and review contract

Additive migration049 follows048; all earlier migrations/history/accepted drafts remain unchanged. Authenticated members use GET `/api/workspaces/[workspaceId]/sites/[siteId]/agency/onboarding` through `bz_agency_onboarding`. The report contains only current approved facts with source/revision/fact/approval references, site preference version/document, the existing authorized preview catalog, three ordered role summaries and the latest reviewed snapshot/history summaries. Unapproved source text, private platform instructions, model credential references and raw provider configuration are excluded.

Each Coordinator/Content/Quality role exposes approved preview count and qualified count. Qualification follows the existing generation preparation criteria: current checked/version-pinned binding, unexpired successful connectivity evidence, enabled current-profile spending policy and unexpired pricing. Zero eligible candidates is a blocker; multiple eligible candidates are also a blocker because the current runtime requires exactly one of each kind. A separate opaque SHA-256 qualification fingerprint covers exact binding/profile/credential/test/policy version identifiers and policy dates/enablement without returning those private records. Thus a binding change cannot escape stale-context detection merely because candidate counts remain unchanged. No readiness display reserves budget or guarantees remaining allowance/provider availability. Execution still uses its existing independent admission and accounting checks.

The analyst-style assessment is deterministic: facts/source counts, missing approved knowledge, absent or ambiguous qualified roles, and optional audience/brand guidance recommendations. It does not infer claims, fetch a site URL, call a provider, appoint a new analyst or promote knowledge. Source text and preferences are displayed as data; they cannot grant permissions. Current qualification expires naturally as tests/pricing age, so users must reload before later decisions.

Owner-only POST uses strict `fingerprint`, `expectedVersion`, `note`, literal `reviewed=true`; server and SQL reject injected activation flags. The database computes the fingerprint over its canonical current snapshot, never a browser-supplied snapshot. Save locks current owner membership/site, checks latest expected review version and current fingerprint, then stores the complete evidence and note as one immutable revision. Snapshot cap256 KiB, maximum50 reviews/site. Identical note/fingerprint saves and an exact lost-response retry by the same actor do not append another revision. A retry may return an already saved historical review together with new current context: the UI marks the saved review historical if fingerprints differ. Different notes at stale versions conflict. No review is automatically declared accepted, no agents are activated, and no generation/spending/publication occurs.

Members can read the latest full saved evidence and bounded historical note/version summaries. Historical full snapshots are retained in the private database; this UI does not offer arbitrary historical snapshot selection. Revoked knowledge disappears from current context but remains in an authorized historical review. Site deletion cascades all reviews. Direct table/function access and service-role execution are revoked except the two authenticated session RPCs; former/unrelated members cannot read the report.
