## Contract, access and retry behavior

Authenticated POST `/api/workspaces/[workspaceId]/sites/[siteId]/agency/generation` accepts a strict2000-byte command with `id`, `runId`, `expectedVersion`, `expectedCampaignVersion` and `reviewed:true`. Both versions are bounded1–100. The workspace owner must already have a proposed request with an048 campaign handoff. The displayed current campaign title/version is returned as `executionPreparation`; the owner should open the linked campaign to review the exact brief before confirming.

The SQL boundary uses the existing global817030 admission lock first, then checked owner membership, site and request locks. Missing campaign, stale proposal/campaign version, paused roster, invalid current qualification, quotas and reused independent run UUIDs reject without partially changing records. Generation snapshots retain the existing25/campaign quota, and proposal events retain their100/event-version limit. A successful transaction creates one run, immutable request/run/actor/source-version lineage and one proposal event. Direct private-table access and lineage updates are denied; site deletion cascades the lineage.

The browser preserves an attempt UUID for the exact displayed versions on lost-response failure. Exact same-actor retry returns the original linkage, even after later proposal cancellation; it does not make a new snapshot, revive a failed run or execute. A different UUID/version cannot replace an existing linkage. Reopening the page reads the persisted link instead of preparing another run.

`execution` projects the actual generation status, timestamps, campaign version, expected stage count and output availability under existing site-member access. Members can read; only owners can prepare. Stage count is planned stage count, not completed work. Status refresh is a page reload, not background execution. The linked campaign retains detailed stages, accounting, outputs and human reviews. Cancelling or deferring a proposal does not cancel an already linked run or change its spending; cancellation/recovery remain governed by the existing runtime. Separate authorized admin dispatch is still required, and existing roster guards recheck new work.

Older pre051 responses default new projection fields to null without changing history. The existing interface remains usable when051 is missing; new preparation controls appear after051. Direct calls to the new API report missing setup honestly. No new API key, environment field or deployment-setting change is introduced. One new checkbox per eligible request explicitly confirms the displayed request/campaign versions; no free-text field is added.
